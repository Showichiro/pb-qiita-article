# Reactセルフレビュー

PR作成・更新前に、ベースブランチからの最終差分と関連コードを読む。
各指摘は対象行、問題が起きる操作、影響、修正案を具体的に示す。
問題を修正して必要な検証を実施し、PR本文へ結果を残す。

## 確認観点

1. 状態設計: 所有者を明確にし、派生値はrender時に計算する。propsやstateの不要なコピーを持たない。
2. Effect: 外部システムとの同期に使う。操作起点の処理はイベントで扱い、依存関係、タイマー・購読のcleanup、最新値の参照を確認する。
3. コンポーネント: 責務と合成を確認する。描画、検証、通信の混在や、不必要な分割・共通化を避ける。
4. 型: props、イベント、状態遷移、API境界を型で表す。anyや型アサーションで問題を隠さず、外部入力を検証する。
5. 性能: 実際に重い計算・描画、参照安定性が必要な箇所を確認する。memoやTransitionの導入には理由を持つ。
6. アクセシビリティ: semantic HTML、入力ラベル、エラーとの関連、buttonのtype、キーボード・フォーカス操作、pending状態の伝達を確認する。

## このプロダクトでの判断

- 入力中のdraft、URLの条件、採用済み結果の条件は異なる役割を持つ。失敗時に前回結果を保持するための分離を、機械的に重複stateと判断しない。所有者と更新タイミングを説明できること。
- URLはnuqs、サーバーデータはTanStack Queryと共有取得フックの契約に従う。戻る・進む、初期bootstrap、無関係なパラメータ、同じ条件の再試行を確認する。
- 非同期処理は古い応答の上書き、データ世代の混在、失敗・再試行、アンマウント、共有リクエストの扱いを確認する。
- 通信回数を抑えるdebounceと、描画を応答可能に保つTransitionは別の目的。片方で置き換えられると決めつけない。
- SSRのネイティブフォームや未送信入力を尊重する。controlled入力やSuspense、useEffectEventなどの採用自体を必須にせず、要件とライブラリの契約から判断する。
- 派生stateのEffect、不要なprops同期、イベント処理のEffect、意図不明な依存配列省略、cleanup不足、動的リストのindex key、不安定な依存参照を確認する。静的リストなど妥当な例外は理由を記載する。
- API数や命名による加点はしない。テストは観察可能な動作を確認し、実装の写しにしない。

## PR本文の記載例

セルフレビュー: 記事検索と共有フックを対象に、状態所有・履歴復元・競合応答・入力保持・ラベルを確認。履歴移動時に古い応答を採用する問題を修正。関連テスト、型チェック、lint成功。ブラウザ実機確認は未実施。

## hook

`.codex/hooks.json` は起動・再開・コンパクション時と、PR作成ツール呼び出し前にこの手順を通知する。
通知はレビューの自動実行や完了証明ではない。エージェントはAGENTS.mdの手順を実行する。
別スクリプト経由の作成などを完全に検出する仕組みではなく、AGENTS.mdの指示はすべての作成経路に適用する。
Codexで初回使用時は `/hooks` から定義を確認して信頼する必要がある。
hookスクリプトはstdinのイベントを読み、通知用JSONだけを出力する。外部送信やリポジトリ変更は行わない。
